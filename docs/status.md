# 验证状态

## 0.8.8-r12：AVRCP 兜底接管、绑定白名单与并发实测定论（本机执行）

OPPO Enco X4，Intel 蓝牙适配器，48 kHz，1000 kbps，2026-11-14。

### 端点不出现的三层根因

r11 在本机部署后，驱动与服务都装上了，但播放端点始终不出现。逐层排查下来是三个互相叠加的原因：

1. **音频端点栈僵死**。反复装卸自研音频驱动后，PnP 里仍有 `耳机 (LHDC Headphones)` 节点且状态为 OK，但 `IMMDeviceEnumerator` 以全状态掩码枚举返回空，`GetDefaultAudioEndpoint` 报 `ERROR_NOT_FOUND (0x80070490)`。这种「PnP 有、MMDevice 无」的状态只能重启整机恢复，重启 `AudioEndpointBuilder` 无效。
2. **部署回滚把服务设为 Disabled**。失败路径执行了 `Set-Service -StartupType Disabled`，SCM 事件 7040 可见，此后 `Start-Service` 静默无效，服务起不来。
3. **原生 AVRCP 控制器没有被接管**（最终拦路虎）。耳机的原生 AVRCP 控制器 `BTHENUM\{0000110E-…}` 占着 AVRCP PSM，传输驱动开 AVRCP 通道被蓝牙栈拒绝：驱动侧逐通道 `LastNtStatus` 显示 `STATUS_DEVICE_NOT_READY (0xc00000d0)`。绝对音量同步因此失败，`MediaSession` 构造抛错，**整个媒体会话中止**，音频端点随之不出现。

第 3 项的根子在接管记录：部署脚本的 `Set-NativeAvrcpOwnership` 在找不到原生控制器节点时静默跳过并直接返回成功，从不写 `HKLM\SOFTWARE\LHDC-Win\Device\NativeAvrcpInstance`；失败回滚还会把已经写进去的键删掉。服务侧 `claim_avrcp_controller()` 在注册表无记录时直接返回，于是形成「没人接管 → 媒体会话起不来 → 部署失败 → 回滚删掉记录」的闭环。手工写入该键并禁用原生控制器节点后，链路立刻恢复：`channel_open` → `media_channel_open`（入 4096 / 出 679）→ `avrcp_volume_ready` → 正常推流。

服务停止时用独立探针直查驱动，三个通道的 OPEN 都成功（24 ms），媒体通道 `inflight_brbs` 取到实际生效值——说明驱动与链路本身正常，问题在服务侧的接管环节。

### r12 的修复

- 服务在注册表没有记录时，自行枚举设备树找到本耳机的原生 AVRCP 控制器节点（按 `{0000110E-…}` 类 GUID 与 `&<12 位大写地址>_` 匹配），禁用它，并把实例身份写回注册表与 `C:\ProgramData\LHDC-Win\native-avrcp.json`。状态文件按 UTF-8 写入（部署脚本用 `-Encoding UTF8` 读取，UTF-16 会让 `ConvertFrom-Json` 失败并中断部署流程），并带 `WasEnabled: true`，使部署脚本的 `Test-NativeAvrcpOwned` 能识别并保留接管、回滚时能恢复 inbox 控制器。
- 安装绑定不再要求设备先处于微软 A2DP 驱动；交还绑定允许任意 inbox 蓝牙音频驱动（微软 A2DP 或 AltA2DP）。

### 并发 16 实测：瓶颈在无线空口

在途上限从 4 提到 16（注册表 `MediaInflightBrbs`，改值后需重建驱动包让设备重读）后连续播放，与并发 4 基线同口径对比：

| 指标 | 并发 4（基线） | 并发 16 |
|---|---|---|
| 播放段 | 1 段，589 s 连续 | 6 段、共 269 s，中间 5 次计数器重置、9 次媒体通道重开 |
| 驱动侧在途包 | 中位 2，峰值 3 | 顶到 15 |
| BRB 提交到完成耗时 | 中位 4.1 ms，p95 29.6 ms，峰值 81 ms | 中位 86～107 ms，峰值 616 ms |
| 丢弃率 | 2.658% | 8.8%～21.7%（坏段） |
| 在途包龄 | 中位 4.65 ms | 中位 105～130 ms，峰值 372 ms |
| 时间线重同步 | 无 | 280 次 |

并发 16 里在途包数接近 1 的时段，BRB 耗时回到 0.5 ms、丢弃率 2.4%～2.8%，与并发 4 基线一致。也就是说提高并发没有换来吞吐：空口一排队，更多在途包只会让每个包都多等。

**结论：默认在途并发保持 4 不变**，r12 不改默认值。

### 恢复默认并发后的同口径复测

把注册表 `MediaInflightBrbs` 恢复到 4、重新发布驱动包让设备重读之后，本机再跑一段连续播放（2026-11-14 00:18–00:29，ffplay 连续 10 分钟以上真实音频）。三组数据用同一工具按运行段口径回算：

| 指标 | 并发 4（r11 基线，589 s） | 并发 4（恢复后复测，644 s） | 并发 16（269 s，6 段） |
|---|---|---|---|
| 包率 | 199.1 包/秒 | 197.8 包/秒 | 坏段 134～183 包/秒 |
| 丢弃率 | 2.658% | 3.388% | 坏段 8.779%～21.693% |
| 队列水位中位 | 70 ms | 80 ms | 坏段 71～93 ms |
| 驱动侧在途包 | 中位 2，峰值 3 | 中位 1，峰值 3 | 顶到 15 |
| BRB 提交到完成耗时（中位） | 4.12 ms | 0.52 ms | 坏段 86.4～107 ms |
| BRB 提交到完成耗时（p95／峰值） | 29.6 ms／81.1 ms | 28.9 ms／172.9 ms | 109～462 ms／616.6 ms |
| 在途包龄中位 | 4.65 ms | 0.12 ms | 坏段 105～129 ms |
| 在途包龄 p95 | 112.3 ms | 123.8 ms | 坏段 128～372 ms |
| 时间线重同步 | 无 | 无 | 280 次 |

三点结论：

1. **恢复并发 4 后链路回到基线水平**。644 秒一段连续、没有计数器重置，包率 197.8 包/秒（1000 kbps 需要约 200 包/秒），丢弃率 3.388%，与 r11 基线的 2.658% 同一量级；驱动侧在途包中位 1、峰值 3，队列不积压。
2. **周期性抖动依旧存在**。BRB 提交到完成的 p95 仍是 28.9 ms（基线 29.6 ms），在途包龄 p95 仍是 123.8 ms（基线 112.3 ms）。中位数从 4.12 ms 降到 0.52 ms 只是采样相位不同——每秒只取最后一个完成的 BRB，落在抖动窗口内还是窗口外差别很大。
3. **并发 16 的好段与坏段差距悬殊**：好段（在途包数接近 1）与并发 4 完全一致（BRB 0.55 ms、丢弃 2.439%），坏段 BRB 中位涨到 86～107 ms、丢弃最高 21.7%。这就是空口排队，不是并发不够。

## 0.8.8-r10：蓝牙发送并发可调 + 驱动侧诊断（本机执行，听音确认由用户完成）

OPPO Enco X4，Intel 蓝牙适配器，48 kHz／24 bit，2026-11-13。

### 丢音频的定位（本机 14076 条历史播放记录）

| 码率 | 实测包率 | 写完成耗时中位 | 写完成耗时峰值中位 | 队列水位中位 | 出现裁剪的会话占比 |
|---|---|---|---|---|---|
| 400 | 101 包/秒 | 约 0.1 ms | 259 ms | 10 ms | 56% |
| 500 | 101 包/秒 | 约 0.1 ms | 51 ms | 10–55 ms | 62% |
| 900 | 201 包/秒 | 约 0.1 ms | 58 ms | 15–59 ms | 39% |
| 1000 | 201 包/秒 | 约 0.1 ms | 177 ms（最大 496 ms） | 54–64 ms | **100%** |

结论：丢失全部发生在服务侧 PCM 队列裁剪上（`discarded_pcm_bytes_total` > 0，`kernel_dropped_bytes_total` 恒为 0，驱动环形缓冲一次都没丢过），蓝牙侧无真丢包证据（时间线重同步后 RTP 序号不留空洞）。各码率包率都达标、写完成耗时中位只有约 0.1 ms，说明软件提交路径不慢；1000 kbps 的 13 段会话 100% 出现裁剪，2610 秒累计丢 21 MB（约 115 秒音频，丢失率 4.4%）。900 与 1000 kbps 包率相同，差异只在每包字节数（578 与 640），指向一个与单包大小相关的阈值。

### 驱动侧关键事实

- `NumberOfPresentedRequests = 4` 对并行队列有效（KMDF 1.9+），请求在传输完成前一直占配额，因此同时进入蓝牙栈的最多 4 个 BRB；服务侧却以为在途约 19 个包，其余堵在驱动队列里，`pending_age` 因此混入排队时间，不是真实链路延迟。
- 媒体队列 `SynchronizationScope = WdfSynchronizationScopeQueue` 让回调串行，但回调本身很短（提交峰值 1 ms），不是吞吐瓶颈。
- 服务等待蓝牙完成超时 500 ms 后会取消并抛异常，整场会话退出，没有中间态。

### 本次改动

- 并发上限改为读注册表 `HKLM\SOFTWARE\LHDC-Win\MediaInflightBrbs`（缺省 4，非法值回退），**默认行为与 r9 一致**；队列在创建设备时固定，改值后需重载驱动才生效。
- 驱动新增诊断并经 `LHDC_INFO` 暴露：`AclMode`（协商到的链路模式）、`MaxBrbLatencyUs` / `LastBrbLatencyUs`（BRB 提交到完成的真实耗时）、`BrbCompletions`（累计完成数）、`InflightBrbs`（实际生效的并发值）。服务每秒读取一次，写入 `direct_audio_progress`。
- 移除媒体通道 `QUERY_INFO` 中的链路模式查询：它在媒体队列同步域内发一次同步 BRB，会占用一个在途名额；链路模式改为通道打开时采集一次。
- ABI 3 → 4，`LHDC_INFO` 80 → 112 字节，驱动与服务必须同版本部署；混装时服务以 `Transport info ABI mismatch` 明确失败。
- 传输驱动包版本升到 0.8.8.3（音频 INF 未改动，保持 0.8.8.2）。

### 待验证

按 4 / 8 / 12 / 16 扫描并发（每档需重载驱动并连续播放 ≥10 分钟），对比 `queue_ms` 中位、裁剪次数、`driver_pending`、`brb_max_latency_us`、`brb_completions` 每秒差分与 `acl_mode`：

- 并发 16 时队列水位降到约 20 ms 以内且裁剪归零 → 并发是主因，保留该值。
- `driver_pending` 长期远低于上限而延迟仍高 → 瓶颈在空口，驱动侧只能减负，需转向链路档位与码率。

### 部署过程记录（r10）

传输驱动 0.8.8.3 已正确装上并与组件逐字节一致（`lhdc-transport.inf_amd64_90bb8bd2dc7e201e`，27912 字节，sha256 前缀 `977FD8B3`）。音频驱动代码未改，INF 保持 0.8.8.2，Windows 按 INF 内容复用既有驱动包。

部署过程暴露两处流程问题，都不是编码问题：

1. **音频子设备无法通过子列表移除**。`lhdc-host audio-detach` 失败：`Transport completion (IOCTL=0x226000, NTSTATUS=0xc000000d) failed, Win32=87`，即向蓝牙栈请求移除子设备时被判定为参数无效。改用 `lhdc-device restore` 先把绑定交还微软 A2DP（绑定重建会连带移除子设备），随后部署才能继续。以后更新驱动若再次卡在同一步，先走"交还 A2DP 再安装"这条路。
2. **Windows 播放端点未激活**。绑定与驱动都成功，KS filter 可用（`direct_formats` 返回 48000/16/2ch，`direct_pcm` 显示 epoch=2 且格式已协商），系统里也存在 `耳机 (LHDC Headphones)` 端点且 PnP 状态为 OK，但 `IMMDeviceEnumerator` 以 `DEVICE_STATE_ACTIVE` 枚举时看不到它，`lhdc-host audio-devices` 因此返回空，部署脚本的格式验证随之失败。此时服务反复报 `LHDC headphone volume endpoint is unavailable`。判断为多次绑定切换与服务停止之后音频端点栈的陈旧状态（r9 时代同样是在重启后才完成验收），需重启电脑后复核；若重启后端点仍不出现，再回头怀疑 r10 驱动本身。

## 0.8.8-r11：修复媒体通道打开回归，定位 1000 kbps 丢音频的真正来源（本机执行）

本机排查记录，OPPO Enco X4，Intel 蓝牙适配器，48 kHz／16 bit，2026-11-13。

### r10 的打开回归：现象与定位

r10 部署后服务建立不起媒体通道：不再产生 `direct_audio_progress`，日志持续输出
`Transport completion (IOCTL=0x22e004, NTSTATUS=0xc00000d0) failed, Win32=71`。
把 IOCTL 码按 `CTL_CODE` 拆开，`0x22e004` 正是 `IOCTL_LHDC_OPEN`（设备类型 0x22、功能号 0x801、读写访问、BUFFERED），
`0xc00000d0` 是 `STATUS_DEVICE_NOT_READY`。重启服务、关闭 EncoDeck、重新部署组件都不改变这一结果。

驱动对 OPEN 只有两处拒绝条件：`ctx->Ready` 为假（设备被电源管理挂到 D3）或 `ctx->SessionClosing` 为真。
用独立探针在服务停止时直接对驱动发 `IOCTL_LHDC_QUERY_INFO`：三个通道都正常返回 112 字节、`Header.Version=4`、
`Header.Size=112`，说明驱动状态与 ABI 都健康，且 `Ready` 为真、`SessionClosing` 为假。
服务运行期间同一个查询却失败，服务日志里也没有出现 `Transport info ABI mismatch`，
因此差异不在协议层，而在服务持有句柄期间设备所处的状态。

差异来自 r10 的一处改动。链路模式查询（`BRB_ACL_GET_MODE`）在 r9 起一直发生在媒体通道打开**之后**；
r10 把它提前到打开**之前**，并且去掉了"没有 WPP 订阅就跳过"的前置判断，于是这次同步 BRB 一定会发出。
链路尚未进入活动状态时该请求要等到超时才返回，打开流程被拖住，随后以设备未就绪失败；
r9 之所以长期稳定，正是因为没有订阅时那次查询会被整段跳过。

### 修复

查询移回媒体通道打开之后（`IOCTL_LHDC_QUERY_INFO` 分支，媒体通道且已连接时执行），
打开路径上不再有同步请求。传输驱动包版本升到 0.8.8.6。修复后服务可正常建立媒体通道，
每秒进度记录里的 `acl_mode` / `inflight_brbs` / `driver_pending` / `brb_max_latency_us` /
`brb_last_latency_us` / `brb_completions` 全部恢复输出。

### 1000 kbps 丢音频的真实来源

以并发 4、1000 kbps、连续 10 分钟真实音频测量（`build\tooling\measure-run.ps1`，
逐分钟分段见 `build\lhdc-r10\run-clean-10min.log`）：

| 指标 | 实测 |
| --- | --- |
| 包率 | 199 包/秒（1000 kbps 每包一帧，需要约 200 包/秒） |
| BRB 提交到完成耗时 | 在 0.5 ms 与 18 ms 之间**周期性摆动** |
| 驱动侧在途数 | 中位 2，最大 3（上限 4） |
| 在途包龄中位数 | 0.1 ms（低延迟段）↔ 58 ms（高延迟段） |
| PCM 队列 | 中位 70 ms，p95 105 ms，上限 120 ms |
| 丢弃率 | 与延迟同步：低延迟段 0～0.65%，高延迟段 4.6～5.2% |

即包率本身达标，丢音频发生在**无线侧的周期性抖动**到来时：4 个在途名额在 18 ms 的抖动窗口内来不及周转，
队列顶到 120 ms 上限后被裁剪。写完成耗时中位数仍只有约 0.1 ms，软件提交路径不是瓶颈。

对照实验支持同一结论：服务在 r10 回归期间反复失败重试，队列与在途状态被拖住时，同一并发值下
BRB 延迟中位数是 23～26 ms、丢弃率 17%；把设备状态清空后，同样的并发值延迟回到 1～4 ms、丢弃率降到 1.6%。
因此"并发不足"与"状态被拖住"必须分开看：**并发 4 不足以吸收 18 ms 的周期性抖动**，而回归本身又制造了额外拥塞。

### 调整并发需要重启系统

并发上限由 `HKLM\SOFTWARE\LHDC-Win\MediaInflightBrbs` 控制，驱动在创建设备时读取一次。本机实测：

- `pnputil /restart-device` 对该蓝牙软设备返回"需要重新启动系统才能完成配置操作"；
- 从 DriverStore 删除驱动包不会卸载已经加载的驱动，设备反而回退到系统自带驱动，绑定需要重建；
- 重新发布新的驱动包（`DriverVer` 递增）会让设备重新创建设备并读到新的注册表值。

因此每一档并发都需要一次系统重启，扫描按 4 → 8 → 16 逐档进行。

## 0.8.8-r9：撤回端点延迟上报，保留实测与日志（本机执行，听音确认由用户完成）

本机排查记录，OPPO Enco X4，Intel 蓝牙适配器，48 kHz／16 bit，2026-11-13。

问题：r8 让驱动把管线延迟填进 `GetHWLatency` 的 `FifoSize`。音频引擎给本端点分配的渲染缓冲是 1056 帧（22 ms），设备周期 10 ms，实测引擎只接受不超过约 32 ms 的硬件延迟；上报 40 ms 时 `IAudioClient::Initialize` 直接返回 `AUDCLNT_E_BUFFER_SIZE_ERROR`（0x88890016），任何客户端都打不开端点。r8 在 1000 kbps 下上报约 200 ms，端点因此报废，部署脚本在格式就绪检查处失败并执行恢复流程，把蓝牙节点交还给微软 A2DP 驱动，表现为耳机彻底没有声音。

实测边界（每次改值后重建端点，`DeclaredLatencyMs` 临时覆盖项驱动）：

| 上报值 | 端点可用 | `IAudioClient::Initialize` | `GetStreamLatency` |
|---|---|---|---|
| 0 ms | 是 | 成功 | 0 ms |
| 10 / 20 / 30 ms | 是 | 成功 | 0 ms |
| 40 / 50 / 80 / 120 / 200 ms | 否 | `AUDCLNT_E_BUFFER_SIZE_ERROR` | 读取失败 |

两条结论：一是超过约 32 ms 会被引擎拒绝，且端点一旦失败就不可恢复，必须重启整机；二是即使在被接受的区间内，`IAudioClient::GetStreamLatency` 仍然返回 0，播放器通过标准接口拿不到该值。

改动：驱动不再声明硬件延迟，`FifoSize` 回到 0，`LHDC_PCM_LATENCY` 属性与相关通道一并撤除；服务继续按实测公式计算管线延迟（PCM 队列水位 + 在途包龄 + 编码间隔 20 ms，无实测时按码率估算 1000 kbps 约 200 ms、其余约 50 ms），以 `pipeline_latency_ms` 写入 `direct_audio_progress` 日志。码率维持 1000 kbps，按用户决定接受该档位的丢包。

驱动包版本升到 0.8.8.2：驱动二进制每次重建都不同（签名带时间戳），INF 版本不变时 Windows 会复用已发布的驱动包目录并保留旧二进制，r8 已为此加入"安装后核对系统实际加载的镜像与随包二进制逐字节一致"的检查。

| 码率 | 有声时长 | 丢弃 | 时间线重同步 | 队列水位中位 | 在途包龄峰值 | 发送等待峰值 | 包率 |
